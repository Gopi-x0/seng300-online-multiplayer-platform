# 03.02 Authentication Use Case Descriptions
# Multiplayer Game Platform — Platform Core Sub-Team

---

## AUTH-01: Register Account

**Primary actor:** Player
**Goal:** Create a new account to access the Multiplayer Game Platform and its games
(Tic-Tac-Toe and Connect Four).
**Preconditions:** Player does not have an existing account and is not currently authenticated.

**Trigger:** Player selects "Register" on the platform welcome/login screen.

**Main success scenario:**
1. System displays the registration form.
2. Player enters required fields: username (or email), password, and display name.
3. System validates all input (format rules, required fields, minimum password length/complexity).
4. System checks that the username/email is not already taken in the User Store Stub.
5. System creates a new PlayerAccount in the User Store Stub, initialized with:
   - Display name, username, hashed password
   - Tic-Tac-Toe stats: gamesPlayed = 0, wins = 0, losses = 0, draws = 0
   - Connect Four stats: gamesPlayed = 0, wins = 0, losses = 0
   - Empty recent match history
6. System confirms registration success and navigates the Player to the login screen
   (or optionally logs the Player in automatically).

**Postconditions:**
- Account exists in the User Store Stub.
- Player profile is initialized with zeroed game statistics for both Tic-Tac-Toe and Connect Four.

**Alternative flows:**
- Step 3 — Invalid input: System highlights invalid fields with error messages and
  returns the Player to the form.
- Step 4 — Identifier taken: System informs the Player that the username/email is already
  in use and prompts for a different identifier.

**Notes for stub implementation:**
- Use HashMap<String, PlayerAccount> where PlayerAccount stores credentials and a
  GameStats object (ticTacToeStats, connectFourStats).
- HashMap version: in-memory persistence for the duration of the run.
- File version: serialize the map to a file at startup; persist after each registration.

## AUTH-02: Log In

**Primary actor:** Player (registered but not yet authenticated)
**Goal:** Authenticate using an existing account to access all platform features,
including game lobbies for Tic-Tac-Toe and Connect Four.
**Preconditions:** Player has a registered account in the User Store Stub.

**Trigger:** Player selects "Log In" on the platform welcome screen.

**Main success scenario:**
1. System displays the login form.
2. Player enters their username/email and password.
3. System looks up the account in the User Store Stub by the entered identifier.
4. System verifies the entered password matches the stored credentials.
5. System creates an authenticated session (e.g., sets currentPlayer to the matched
   PlayerAccount object).
6. System navigates to the Platform Dashboard, which displays:
   - Available games (Tic-Tac-Toe and Connect Four)
   - Active game lobbies the Player may join
   - Leaderboard standings
   - The Player's current stats summary

**Postconditions:** Player is authenticated; currentPlayer session variable is set to
the matching PlayerAccount.

**Alternative flows:**
- Steps 3–4 — Account not found or password mismatch: System displays a generic
  "Invalid username or password" message (do not distinguish between the two for
  security) and returns the Player to the login form.
- Optional: After N consecutive failed attempts, system temporarily disables login
  for that account and displays a lockout message.

**Notes for stub implementation:**
- Session: currentPlayer is an in-memory reference to the authenticated PlayerAccount.
- All platform features that require authentication (joining a Tic-Tac-Toe or
  Connect Four lobby, viewing the leaderboard, editing profile) must guard against
  currentPlayer == null before proceeding.

## AUTH-03: Reset Password

**Primary actor:** Player (unauthenticated; forgot or lost credentials)
**Goal:** Replace a forgotten or compromised password with a new one.
**Preconditions:** Player has a registered account in the User Store Stub and is not
currently authenticated.

**Trigger:** Player selects "Forgot Password?" on the login screen.

**Main success scenario (stub-friendly — email simulation method):**
1. System displays the password reset screen.
2. Player enters their registered username or email.
3. System verifies the account exists in the User Store Stub.
4. System generates a random 6-digit one-time reset code, stores it temporarily in
   the PlayerAccount, and displays it on-screen (simulating an email delivery).
5. Player enters the displayed reset code.
6. System validates the entered code against the stored code.
7. Player enters a new password and confirms it (re-enters).
8. System validates the new password:
   - Meets minimum length and complexity rules
   - Differs from the current stored password
9. System updates the stored password in the User Store Stub and clears the reset code.
10. System confirms the reset with a success message and navigates the Player to
    the login screen.

**Postconditions:** Stored password is updated in the User Store Stub; one-time reset
code is cleared.

**Alternative flows:**
- Step 3 — Account not found: System displays an error message and returns to step 2.
- Step 6 — Incorrect code entered: System displays an error; optionally limits retry
  attempts (e.g., 3 attempts before invalidating the code).
- Step 8 — Weak or reused password: System prompts the Player to choose a different
  password and returns to step 7.

**Notes for stub implementation:**
- Add a resetCode field (String, nullable) to PlayerAccount.
- Generate the code using Random or UUID; display it in a dialog/label on the reset screen.
- This flow requires no external services and is entirely in-memory.
- Chosen method: email simulation (displays code on-screen). Security question method
  is an alternative: store a securityQuestion and securityAnswer in PlayerAccount and
  validate in step 6.

## AUTH-04: Log Out

**Primary actor:** Authenticated Player
**Goal:** Safely end the current authenticated session and return to the welcome/login screen.
**Preconditions:** Player is authenticated (currentPlayer != null).

**Trigger:** Player selects "Log Out" from the Platform Dashboard navigation bar or
from the in-game menu.

**Main success scenario:**
1. System checks whether the Player is currently in an active Tic-Tac-Toe or
   Connect Four game match.
2. If no active match: System proceeds directly to step 4.
3. If active match exists: see Alternative Flow below.
4. System clears the authenticated session (sets currentPlayer = null).
5. System discards any temporary in-memory session data (e.g., pending match state,
   in-progress lobby status).
6. System navigates to the welcome/login screen.

**Postconditions:** currentPlayer is null; Player is no longer authenticated; no active
session data remains in memory.

**Alternative flows:**
- Step 1 — Player is in an active Tic-Tac-Toe or Connect Four match:
  a. System displays a confirmation dialog:
     "You are currently in an active match. Logging out will forfeit the game. Continue?"
  b. If Player selects "Cancel": System dismisses the dialog and returns the Player
     to the active game. Use case ends.
  c. If Player selects "Confirm": System records a loss/forfeit for the logging-out
     player and notifies the opponent of the win via the Platform Core game state
     manager. The PlayerAccount game stats (ticTacToeStats or connectFourStats) are
     updated accordingly in the User Store Stub. System then proceeds with steps 4–6.

**Notes for stub implementation:**
- Check currentGame != null (or equivalent lobby/session state) before clearing the session.
- The forfeit outcome must be handled through the Platform Core's game state manager,
  not directly by the auth system — the auth system only triggers the end-of-game event.

## AUTH-05: View / Edit Profile

**Primary actor:** Authenticated Player
**Goal:** View personal account information and game performance statistics for both
Tic-Tac-Toe and Connect Four, and optionally update editable profile fields.
**Preconditions:** Player is authenticated (currentPlayer != null).

**Trigger:** Player selects "Profile" or "My Account" from the Platform Dashboard.

**Main success scenario:**
1. System retrieves the authenticated player's full profile from the User Store Stub
   using currentPlayer.
2. System displays the profile page with the following information:
   - Username and display name
   - Tic-Tac-Toe statistics: games played, wins, losses, draws, win rate (%)
   - Connect Four statistics: games played, wins, losses, win rate (%)
   - Recent match history: last 10 games across both game types, showing
     game type, opponent username, result (Win/Loss/Draw/Forfeit), and date/time
   - Current platform leaderboard rank (if available)
3. Player optionally selects "Edit Profile."
4. System displays an editable form pre-populated with the Player's current display
   name and email address. The password field is not shown here — password changes
   use AUTH-03 (Reset Password).
5. Player updates the desired fields.
6. System validates updated inputs:
   - Display name: non-empty, max character limit
   - Email: valid format and not already taken by another account
7. System saves the validated updates to the User Store Stub.
8. System displays a success confirmation message and returns to the profile view
   (step 2).

**Postconditions:** Updated profile fields are persisted in the User Store Stub and
reflected on the profile view.

**Alternative flows:**
- Step 3 — Player does not select Edit: Player views the profile read-only. Use case
  ends after step 2.
- Step 6 — Validation fails (blank display name, invalid or taken email): System
  highlights the invalid fields with error messages and returns the Player to step 5.

**Notes for stub implementation:**
- PlayerAccount should contain:
    String username, displayName, email
    GameStats ticTacToeStats  // gamesPlayed, wins, losses, draws
    GameStats connectFourStats // gamesPlayed, wins, losses
    List<MatchRecord> recentMatches // gameType, opponentUsername, result, timestamp
- Game stats (wins/losses/draws) are updated by the Platform Core's game state
  manager when a game concludes — not directly by the auth system.
- The auth system is responsible only for reading and displaying stats, and for
  persisting editable fields (displayName, email).
- Win rate calculation: winRate = (wins / gamesPlayed) * 100, defaulting to 0.0
  when gamesPlayed == 0 to avoid division by zero.
